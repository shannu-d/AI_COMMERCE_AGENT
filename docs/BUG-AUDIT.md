## 1. Audit Scope

This audit is a complete, code-level and runtime verification of the Merchant AI Commerce Agent prior to its Razorpay Buildathon submission. The audit was conducted by executing tests, inspecting git commit history, querying live PostgreSQL instances, validating API contracts, verifying cryptographic signatures, and testing failure modes across the following systems:

- **Architecture & Foundation:** Configuration models (`app/config.py`), logging redaction filters, and error handlers.
- **Catalog & Seed Data:** Schema migrations (`alembic/versions/`), seed definitions (`app/seed/`), category trees, SKU uniqueness, and compatibility rules.
- **Deterministic Ranking & Recommendation:** Multi-objective scoring (`app/ranking/`), hard constraint filters (budget, inventory, compatibility), and weight profiles.
- **AI Agent Runtime & Tooling:** Tool schema contracts (`app/llm/tools/`), Groq OpenAI-compatible client (`app/llm/client.py`), system prompt constraints, and turn execution loops (`app/agent/`).
- **Commerce Flow & Policy Engine:** Session management (`app/services/session_service.py`), cart mutations, version bumping, approval lifecycle (`app/services/approval_service.py`), and the pure 10-rule deterministic Policy Engine (`app/policy/engine.py`).
- **Payments & Webhook Processing:** Order creation, integer minor-unit currency calculations (`app/payments/money.py`), Razorpay client execution (`app/payments/client.py`), and constant-time HMAC-SHA256 webhook signature verification (`app/api/routes/webhooks.py`).
- **Authentication & Security Boundaries:** Argon2id password hashing, session ownership claiming, merchant multi-tenant isolation, and IDOR access control (`app/api/routes/auth.py`, `app/api/routes/account.py`).
- **Storefront Frontend:** React 18 / Vite frontend, Assistant UI runtime integration, cart synchronization, and payment checkout bindings.
- **External AI Buyer Surface:** Model Context Protocol (MCP) server implementation (`app/mcp/`).

## 3. Bugs By Area

### AI Agent
- **[BUG-008](bugs/search-catalog-tool-parameters-f3.md) (FIXED):** Undescribed tool schema in `search_catalog` caused technical requirements ("noise-cancelling earbuds") to be treated as soft text relevance instead of an eliminating attribute filter, causing non-ANC products to be recommended with false prose claims.
- **[BUG-006](bugs/llm-rate-limit-retry-exhaustion.md) (FIXED):** Sub-second fixed exponential backoff exhausted all retries within 2 seconds when Groq's 8,000 TPM rate limit was hit on multi-leg turns, causing agent turns to crash.
- **[BUG-010](bugs/unsolicited-agent-cart-creation.md) (FIXED):** The agent proactively called `propose_cart` and `request_approval` on purely informational product queries, demanding immediate payment approval from browsing buyers.
- **[BUG-015](bugs/llm-prose-hallucination-f1.md) (CONFIRMED BUG — OPEN):** The natural language `message` generated by the model can hallucinate nonexistent SKUs and prices (e.g. `CASE-IP16-PRM` or fake discounts) under specific adversarial probes, even though the structured recommendation and payment pipeline remains completely unaffected.

### Catalog & Product Data
- **[BUG-014](bugs/catalog-seed-constraint-key-error.md) (CONFIRMED BUG — OPEN):** An uncommitted data replacement in `catalog.json` renamed `wattage` to `output_wattage` on three wireless chargers with `minimum_wattage` compatibility constraints, crashing `test_every_constraint_predicate_is_satisfied_by_its_own_product` with `KeyError: 'wattage'`, while deleting multi-category trees required by ADR-021.
- **[BUG-011](bugs/ambiguous-orm-category-foreign-keys.md) (FIXED):** Composite merchant-scoping foreign keys alongside standard category foreign keys caused SQLAlchemy's ORM mapper to crash with `AmbiguousForeignKeysError` on `Category.products`.

### Recommendation & Ranking
- **[BUG-013](bugs/test-top-k-regression.md) (REGRESSION — OPEN):** When `RANKING_TOP_K` default was increased from 3 to 9 in commit `9413bb5`, `tests/services/test_recommendation_service.py::test_top_k_caps_the_result_at_three` was not updated and failed with `AssertionError: assert 8 <= 3`.

### Compatibility
- *Audit Finding:* No confirmed compatibility logic bugs found in the active codebase. Normalization, target alias resolution (e.g. "iphone16" -> "iphone_16"), and constraint predicate evaluation pass 49/49 tests.

### Inventory
- *Audit Finding:* No confirmed inventory service bugs found. Stock checks are executed at lookup, at cart addition, and strictly re-checked in the Policy Engine immediately before order creation.

### Cart
- **[BUG-005](bugs/add-to-cart-anonymous-session.md) (FIXED):** The "Add to Cart" button rendered permanently disabled for any first-time anonymous visitor because the component checked for session presence at render time and failed to invoke `ensureSessionId()`.
- **[BUG-007](bugs/chat-cart-serialization-mismatch.md) (FIXED):** `serialize_cart` in `app/agent/service.py` omitted `status` and `price_changes`, creating a contract mismatch with the frontend Zod schema and causing the browser to discard agent turns with `MALFORMED_RESPONSE`.

### Approval & Policy Engine
- **[BUG-002](bugs/price-drift-approval-rollback-loop.md) (FIXED):** `POST /api/cart/approve` executed `db.rollback()` upon detecting price drift on a stale version, wiping out the newly updated prices and trapping buyers in an unrecoverable infinite retry loop.
- *Policy Engine Invariant:* The Policy Engine itself is implemented as a pure, deterministic function evaluated in memory against fresh database rows. All 38 policy engine unit tests pass.

### Payments & Razorpay
- **[BUG-001](bugs/undeclared-razorpay-dependency.md) (FIXED):** The `razorpay` Python SDK was omitted from `backend/pyproject.toml`, resulting in HTTP 503 errors during live checkout despite valid credentials being present in `.env`.
- **[BUG-004](bugs/non-hermetic-test-suite-live-payments.md) (FIXED):** `tests/conftest.py` allowed Pydantic to read `.env` during test execution, causing test runs to make live API calls to Razorpay and polluting the test account.

### Webhooks
- *Audit Finding:* Webhook handling is sound. Verification runs against the raw request body bytes before JSON decoding, uses constant-time HMAC comparison, and enforces database-level deduplication via a unique constraint on `(provider, event_id)`. All 23 tests pass.

### Idempotency
- *Audit Finding:* Order idempotency keys are minted exclusively by the server during approval. Client-invented keys are rejected with HTTP 400. Replaying a valid idempotency key returns the existing order with `replayed: true` without duplicating rows or provider calls.

### Database & State
- **[BUG-009](bugs/stale-session-storage-deadlock.md) (FIXED):** Re-seeding the database caused browsers holding cached session IDs to receive 404 errors indefinitely, locking the chat interface until `sendWithSessionRecovery` was added to purge stale storage.

### API & Configuration
- **[BUG-012](bugs/missing-cors-and-pydantic-config-crash.md) (FIXED):** Backend lacked CORS middleware entirely, blocking browser traffic across origins. In addition, setting `CORS_ALLOWED_ORIGINS` as a comma-separated string caused Pydantic Settings to crash at startup attempting `json.loads`.

### Frontend
- Frontend Vitest suite passes 71/71 tests. User actions are gated behind valid mutations, amounts are never trusted from the client, and Assistant UI handles server errors cleanly.

### Security & Authorization
- **[BUG-003](bugs/order-ownership-session-hijacking.md) (FIXED):** Order ownership derived through anonymous sessions resulted in orders not reaching customer accounts, while logging into a merchant account from the same browser claimed the session and locked the order behind a 403 response.

### Failure Recovery
- Graceful degradation verified across:
  - Upward and downward price drift (re-prices cart, bumps version, returns 409/422).
  - Out of stock before payment (blocks checkout, records audit event).
  - Failed payment webhook (`payment.failed` marks order `PAYMENT_FAILED` without deleting cart).

## 4. Most Important Finding

The single most critical bug identified and resolved during this project was **[BUG-002: Price-Drift Approval Rollback Infinite Loop](bugs/price-drift-approval-rollback-loop.md)**.

### Why It Mattered
The defining value proposition of this architecture is its financial safety spine:
```
LLM proposes → application validates → user authorizes → Razorpay executes → system audits
```
When catalog prices change between a user's initial browsing and their checkout, the system promises to protect the buyer by refusing to charge the unapproved amount and walking them through a transparent re-approval of the updated total.

Because `POST /api/cart/approve` caught `ApprovalError` and called `db.rollback()`, the database rolled back the very price-update that was supposed to resolve the drift. The HTTP response informed the client that the cart was at `current_version: 2`, but the database row remained at `version: 1`. Every subsequent click resulted in another version mismatch, another rollback, and another error. 

This bug turned the system's headline safety feature into an inescapable dead end. Fixing it by committing the price refresh before raising the 409 error allowed the recovery workflow to function as intended: stale version detected → cart updated to current price → buyer re-confirms → payment proceeds safely.

## 5. Money-Path Findings

The money path was verified across the six critical transition boundaries:

```
[User Approval] ──> [Policy Engine] ──> [Razorpay Order] ──> [Payment Checkout] ──> [Signed Webhook] ──> [Final Audit State]
```

1. **User Approval Boundary:**
   - No endpoint accepts an amount or total to charge.
   - `POST /api/cart/approve` accepts only `cart_version` and an optional `expected_total` confirmation.
   - Authorizations carry a strict 15-minute TTL and bind the exact cart item fingerprint. Any modification to cart items immediately marks existing approvals `SUPERSEDED`.
2. **Policy Engine Boundary:**
   - Order creation (`POST /api/orders`) triggers a pure 10-rule policy evaluation.
   - Live prices and inventory levels are freshly re-queried from PostgreSQL within the transaction.
   - Downward price drift is blocked just as firmly as upward drift (`PRICE_CHANGED`), strictly enforcing that the user authorized the exact total.
   - An unapproved cart or expired approval fails with `APPROVAL_REQUIRED`.
3. **Razorpay Order Creation:**
   - Internal order is committed to PostgreSQL in `ORDER_CREATED` status *before* contacting Razorpay (ADR-011), guaranteeing that a provider outage leaves a durable, traceable order.
   - Amount conversion from decimal rupees (`₹999.00`) to integer paise (`99900`) is handled in a single centralized module (`app/payments/money.py`). Floats are strictly prohibited.
4. **Payment Checkout Boundary:**
   - Frontend Checkout receives `razorpay_order_id` and public `key_id`.
   - The frontend's success callback is explicitly **not** trusted as payment truth. The order status remains `RAZORPAY_ORDER_CREATED` until server verification.
5. **Webhook Handling:**
   - `POST /api/webhooks/razorpay` verifies the raw byte body against `RAZORPAY_WEBHOOK_SECRET` using constant-time HMAC-SHA256 comparison before decoding JSON.
   - Duplicate deliveries are gracefully deduplicated by the database unique constraint on `(provider, event_id)`, returning HTTP 200 `{"status": "ignored"}`.
   - Order state transitions to `PAYMENT_CONFIRMED` only upon processing a verified `payment.captured` or `order.paid` event.
6. **Audit Trail:**
   - Every stage (`USER_APPROVED`, `POLICY_PASS`, `POLICY_FAIL`, `PRICE_CHANGED`, `ORDER_CREATED`, `PAYMENT_WEBHOOK_RECEIVED`, `PAYMENT_CONFIRMED`) writes an immutable, append-only row to `audit_events`.

## 7. Remaining Risks

Based on direct inspection of the codebase and test runs, the following real operational risks remain:

1. **Free-Tier Token Budget Constraints on Live Demos:**
   Groq's free account rate limit is strictly 8,000 tokens per minute. A standard agent turn consumes approximately 9,200 tokens across two calls. While the client properly pauses (~13 seconds) to wait out the bucket refill, rapid conversational pacing during a live demonstration will experience rate-limit pauses or exhaust the daily quota (200,000 tokens/day).
   *Mitigation:* Use the pre-tested prompts in `docs/DEMO-SCRIPT.md` and demonstrate storefront and cart browsing actions that require zero LLM tokens.

2. **Outbound LLM Prose Validation (F-1):**
   While no money can move on hallucinated products, the assistant can still write fabricated SKUs or prices in its prose response. Implementing an outbound grounding filter (Recommendation R-1) remains the highest-value functional improvement for the agent layer.

3. **In-Memory `@lru_cache` on Server Settings:**
   Because `app.config.get_settings` is cached for process lifetime, modifying environment variables in `.env` requires a full worker restart. If configuration is changed without restarting the process, the backend will continue evaluating webhooks or provider requests using stale secrets.

## 8. Audit Conclusion

The Merchant AI Commerce Agent demonstrates exceptional engineering discipline. The core principle — that the Large Language Model is an untrusted client that proposes but never authorizes or executes financial transactions — is strictly enforced at every layer of the architecture.

The 12 fixed bugs documented in this audit trace the genuine evolution of this system: resolving ORM ambiguities, preventing price-drift deadlocks, declaring missing payment dependencies, aligning frontend contracts, and handling provider rate limits. With the documented money-path guarantees verified end-to-end against live Razorpay services, the system is in a strong, defensible state for Buildathon submission.
